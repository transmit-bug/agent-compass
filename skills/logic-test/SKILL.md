# Logic Test

针对"有源码的应用"做业务逻辑测试：读懂代码和页面文案，推断出业务逻辑，按逻辑生成
测试用例，在真实运行的应用上逐条执行，最后把发现的问题分类报告。**不改代码** —— 只
测和报。

适用：Web 应用（agent-browser 驱动）、桌面应用（computer-automation 驱动）、纯后端
或 CLI（直接 Bash）。执行通道是最后一步的分支；前四步与领域无关。

## 依赖

- 执行通道（按应用类型选一个）：
  - **Web**：`agent-browser`（`npm i -g agent-browser && agent-browser install`），命令
    面 `agent-browser skills get core`
  - **桌面**：`computer-automation` 技能的 mid.sh 会话命令（`start / act / assert /
    finish`）
  - **后端 / CLI**：直接 Bash
- 运行记录（可选）：agent-browser 套件的 `agent-browser-run` 脚本，模型见
  `skills/agent-browser/references/session-model.md` —— 没有也能跑，只是少了追溯

## 步骤

1. **读懂业务逻辑。** 读源码（入口 / 路由 / 组件 / 状态 / API 调用），再结合页面文案和
   交互，列出：
   - 核心流程：用户能走的路径
   - 每条路径上的规则：条件分支、必填项、状态变化、副作用（提交 / 跳转 / 写数据）
   - 边界与错误处理：空值、超长、非法格式、接口失败、超时
   产出**逻辑清单**（每条：流程 → 规则 → 预期行为），给用户看，确认或补充。
   *完成条件：清单逐条对照过源码入口和分支，没有漏；用户确认。*

2. **生成测试用例。** 按逻辑清单生成，覆盖要求：
   - 每条逻辑至少一个用例（正常路径）
   - 每个条件分支的 else 边至少一个用例
   - 边界值：空、最小、最大、超长、非法格式
   - 错误路径：接口失败、超时、无效提交
   产出：用例清单（输入 → 操作 → 预期结果），每条标注对应逻辑清单条目。
   *完成条件：清单里每条逻辑都有用例，分支两边都有覆盖。*

3. **跑用例。** 逐条执行：
   - **Web**：agent-browser 驱动；断言用结构方式（`snapshot -i` / `read` / `get count` /
     `eval` / `wait --text`），截图只在"看外观"或"留证据"时用
   - **桌面**：mid.sh 的 `act` / `assert`
   - **后端 / CLI**：跑命令、比对输出与退出码
   每条用例记录：操作、实际结果、期望、通过 / 失败。可复用的用例存成配方文件
   （`.agent-browser/flows/<name>.md`）。
   *完成条件：所有用例都执行完，每条有结果记录。*

4. **分析问题。** 把每个失败或异常的用例归入三类：
   - **实现与逻辑不符**：源码说 A，实际行为是 B → 代码 bug（附源码位置 + 实际证据）
   - **逻辑自身有缺陷**：实现和逻辑一致，但这条逻辑本身就是错的 / 漏了边界 →
     设计缺陷
   - **推断错了**：我误解了业务逻辑 → 修正用例，重新跑
   *完成条件：每个异常都归了类；归"实现不符"的有源码位置，归"逻辑缺陷"的说清缺陷
   在哪。*

5. **报告。** 按三类组织，每条问题带证据：用例、操作步骤、期望、实际、截图或结构
   快照路径。报告不静默结束 —— 给结论、给证据、给建议下一步。

## 参考

- **断言语义**：通过 = 预期可被结构断言验证；预期含糊时给证据问用户，不猜。
- **分类边界**：拿不准"实现不符"还是"逻辑缺陷"时，去源码里找对应分支 —— 分支存在
  但行为偏离是前者；分支或边界根本不存在是后者。
- 探索式找 bug（没有明确逻辑清单的乱逛）是另一件事 —— 那是 agent-browser 的
  `dogfood`，不是本技能。

## 边界

- 不改代码：修问题用 `web-fixer`（Web）或 `ui-fixer`（桌面）。
- 不可逆操作（提交 / 删除 / 覆盖）先问用户。
- 敏感内容不进截图；认证走 agent-browser 的 auth vault，不贴密钥。
